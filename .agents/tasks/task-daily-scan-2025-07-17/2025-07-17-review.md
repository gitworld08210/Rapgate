# Bug fixes, onboarding validation, and water-log undo

Three categories of change: a compile-breaking import removal and auth exception rework, input validation on the onboarding form, and a new undo feature for quick-add water logs. The firebase_auth removal and the exception handling cleanup are clearly necessary — the old code couldn't compile against the Supabase-based codebase. The onboarding validation is straightforward bounds checking. The water undo is a small UX improvement that threads a log ID from the data layer back to the UI for deletion.

**Watch for:** The `requires-recent-login` string match in the delete-account catch block is dead code — the `deleteAccount()` method calls a Supabase Edge Function that throws a generic `Exception('Could not delete the account.')`, so that string will never appear in the thrown message (confirmed). The undo action fires `deleteWaterLog` with no error handling — a network failure is silently swallowed (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The settings screen delete-account flow catches exceptions generically and checks for the string `requires-recent-login`, but `deleteAccount()` invokes a Supabase Edge Function and throws `Exception('Could not delete the account.')` on failure. That condition is unreachable, making the re-auth prompt dead code introduced in this diff.

The onboarding bounds validation is duplicated in `_canProceed()` and `_saveProfile()` as defense-in-depth, but `_saveProfile()` uses `?? 70.0` / `?? 170.0` / `?? 25` fallback parsing before the bounds check. If parsing fails, the fallback values pass validation silently — the secondary check can never trigger on parse failure, only on bounds violations from valid parse results. The fallback defaults mask the condition the second check is trying to catch.

The water-log undo fires `health.deleteWaterLog(logId)` from the SnackBar action with no `try/catch`. A network failure silently loses the undo without user feedback, and no follow-up SnackBar can confirm or report the failure since the original has already dismissed.

## Delete-account exception path is disconnected

The `deleteAccount()` method in `auth_service.dart` invokes a Supabase Edge Function:

```dart
Future<void> deleteAccount() async {
  final response = await supabase.functions.invoke('delete-account');
  if (response.status >= 400) {
    throw Exception('Could not delete the account.');
  }
  await signOut();
}
```

The settings screen catches with `catch (e)` and checks `e.toString().contains('requires-recent-login')`. That condition is unreachable — the exception message is always "Could not delete the account." or an unrelated network error.

The `requires-recent-login` concept comes from Firebase Auth's re-authentication requirement. In the Supabase world, the Edge Function could return a 401/403 indicating session staleness, but the current code doesn't extract or surface that. Either the Edge Function needs to include the string in its error response (and `deleteAccount()` needs to propagate it), or this check should be removed and replaced with a generic error display.

## Water-log undo: silent failure

The undo button calls `health.deleteWaterLog(logId)` directly in `onPressed`:

```dart
onPressed: () => health.deleteWaterLog(logId),
```

No `try/catch` — if the network call fails, the user gets no feedback. The log remains, the undo appeared to work (button was pressed), and the totals silently stay unchanged. The SnackBar disappears after the default ~4 second duration, so even if a wrapper wanted to show a follow-up error message, the original SnackBar context is gone.

## Onboarding double-validation with default masking

In `_saveProfile()`:

```dart
final weight = double.tryParse(_weightController.text) ?? 70.0;
final height = double.tryParse(_heightController.text) ?? 170.0;
final age = int.tryParse(_ageController.text) ?? 25;

// Then checks bounds on these values...
```

If the user reaches `_saveProfile()` with non-numeric text (which `_canProceed()` should prevent, but `TextInputType.number` doesn't guarantee numeric-only input on all platforms), the `?? 70.0` silently substitutes a valid default. The subsequent bounds check passes, and the user gets onboarded with fabricated metrics. Replacing the null-coalesce with a direct null check + early return would close this gap.
