# Push-up session UX overhaul: live feedback, post-session summary, and overview enrichment

This change adds a rich live-session experience (animated countdown, rep quality gauge, haptic feedback, green flash on rep, circular progress ring, camera-failure recovery dialog, network-error toasts) and a full post-session flow (summary screen with confetti on success or improvement tips on failure, session history card, warm-up guide sheet, rest timer after failed sessions). The service layer gains a `RepQuality` enum and three read-only helpers (`getRepQuality`, `sessionDuration`, `avgRepTimeMs`); `processFrame`, `submitBatch`, and the Cloud Functions anti-cheat logic (`pushup.ts`) are untouched.

Watch for: the rest timer never activates because `latestPushupSession` only streams verified sessions (confirmed); `SessionHistoryCard` will only ever display 0 or 1 entries because it's fed from the same single-session stream (confirmed); the `_showRestTimer` state flag logic is contradictory and never allows dismissal to actually remove the widget (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The live session screen replaces the old text countdown and bottom-sheet result with dedicated widgets and a `pushReplacement` navigation to a new summary screen. Haptic feedback, a green border flash on rep, and a quality indicator overlay give the user real-time feedback without touching the frame-processing pipeline. Error recovery improves: a Retry button on initialization failure, a recovery dialog when the camera stream dies mid-session, and a non-intrusive SnackBar when batch verification encounters a transient network error.

The rest timer, session history card, and warm-up sheet add surface area to `pushup_screen.dart`, which converts from `StatelessWidget` to `StatefulWidget` to track dismissal state. However, the rest timer's data dependency — `HealthProvider.latestPushupSession` — only ever contains a *verified* session, so the `status == failed` check can never pass and the timer is effectively dead code. Session history has the same data gap: it receives at most a single verified session, making the "last 5 sessions" layout unreachable without a broader Firestore query.

The summary screen computes a form-quality score from face-visibility ratio and average rep time, rendered as a segmented progress bar with contextual tips on failure.

<summary>Issues (5)</summary>

1. **Rest timer is dead code** — `_shouldShowRestTimer` checks `status == failed`, but `streamLatestPushupSession` filters to `status == 'verified'`. The timer will never render. Wire up a stream/query that includes failed sessions, or store the last session outcome locally.
2. **Session history only shows 0-1 entries** — `SessionHistoryCard` is designed for up to 5 sessions but only ever receives the single latest verified session from `HealthProvider`. Add a list query (e.g., last 7 days) or pass stored session data.
3. **`_showRestTimer` state logic is contradictory** — `_shouldShowRestTimer` returns `false` once `elapsed >= 2 min`, but `_showRestTimer = true` (set on dismiss/complete) is never checked inside `_shouldShowRestTimer`, so the `if (_shouldShowRestTimer(health))` guard still controls visibility. The `needsRest` / `showRest` local variables are computed but unused.
4. **SnackBar stacking on repeated batch failures** — `_submitBatch` fires every 10 s; multiple transient failures will stack SnackBars on top of each other. Use `ScaffoldMessenger.of(context).clearSnackBars()` before showing a new one, or deduplicate with a cooldown flag.
5. **Warm-up sheet bypass while rest timer active** — The "Warm up first" link calls `_navigateToSession` directly on completion, bypassing the rest-timer-disabled state of the main Start button. A user resting can tap "Warm up first → Start Session" in the sheet and skip the lock.

## Rest timer data mismatch

`_shouldShowRestTimer` inspects `health.latestPushupSession` and checks whether its status is `PushupSessionStatus.failed`. The underlying Firestore query in `streamLatestPushupSession` applies `.where('status', isEqualTo: 'verified')` and orders by `completedAt` descending:

```dart
// firestore_service.dart:167
Stream<PushupSessionModel?> streamLatestPushupSession(String uid) {
  return _pushupSessionsCol(uid)
      .where('status', isEqualTo: 'verified')
      .orderBy('completedAt', descending: true)
      .limit(1)
      ...
}
```

The result is always a verified session or `null`. The `status != failed` early-return in `_shouldShowRestTimer` guarantees the method always returns `false`. The `RestTimerWidget` and associated button-disabling logic are unreachable.

## Session history data gap

`SessionHistoryCard` accepts `List<PushupSessionModel>` and renders up to 5 entries with timeline dots, dates, rep counts, and PASS/FAIL/PENDING badges. The call site constructs the list as:

```dart
sessions: health.latestPushupSession != null
    ? [health.latestPushupSession!]
    : [],
```

This will only ever be a zero- or one-element list of a verified session. The FAIL and PENDING paths in `_SessionRow` are unreachable from production data.

## `_showRestTimer` state confusion

Three variables participate in the rest-timer visibility logic:

```dart
final needsRest = _shouldShowRestTimer(health) && !_showRestTimer;
final showRest = needsRest && !_showRestTimer;
```

`showRest` is never referenced in the build tree — the widget tree uses `if (_shouldShowRestTimer(health))` directly. When `onComplete` fires, it sets `_showRestTimer = true`, but `_shouldShowRestTimer` doesn't consult `_showRestTimer`, so the widget remains visible until the 2-minute window expires naturally. The `_showRestTimer` field and the `needsRest`/`showRest` locals are dead code.

## SnackBar accumulation during network instability

`_submitBatch` shows a floating SnackBar on every `catch`. With a 10-second batch interval and sustained network loss, SnackBars will queue and visually pile up. `SnackBarBehavior.floating` with custom margins does not automatically dismiss previous entries. A `clearSnackBars()` call before showing, or a cooldown flag that suppresses duplicates within 30 s, would prevent the accumulation.

## Warm-up sheet bypasses rest lock

When the rest timer is active, the primary "Start Session" button is disabled (`onPressed: null`). The "Warm up first" link remains tappable:

```dart
GestureDetector(
  onTap: () {
    WarmupGuideSheet.show(
      context,
      onStartSession: () => _navigateToSession(context),
    );
  },
```

Inside the sheet, "Start Session" calls `_startSession()` → `widget.onStartSession()` → `_navigateToSession(context)`. This path doesn't check the rest-timer state, so a user can begin a new session while supposedly locked out by the rest timer.
