# Daily maintenance: bug fixes, input validation, midnight timer, notifications, and premium paywall

This change fixes four bugs (a stale Firebase import breaking compilation, raw-String exception throws, missing onboarding validation, and a stale-date stream bug) and adds two revenue-driving features (scheduled notification reminders with a settings UI, and a premium subscription paywall with dashboard upsell). The approach is conservative on the fixes — the midnight timer is a minimal addition, the exception class follows existing patterns — and additive for features, creating three new screens and extending the notification service. Watch for: **timezone `tz.local` defaults to UTC** because `flutter_timezone` is added as a dependency but `tz.setLocalLocation()` is never called (confirmed), and the **cancel-all-then-reschedule pattern** in reminder toggles creates a window where notifications can be lost.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The Firebase-to-Supabase migration had a leftover `firebase_auth` import in settings_screen.dart that made the app uncompilable. This PR removes it and replaces the typed catch with a generic one. However, the catch now string-matches `'requires-recent-login'` — a Firebase error code that can never appear in the Supabase Edge Function response — making the re-login prompt path dead code.

Exception handling in auth_service.dart graduates from throwing raw Strings to an `AppAuthException` class. One inconsistency remains: `_validateUsername` still throws a raw String, so callers catching `AppAuthException` will miss username validation failures.

Onboarding gains bounds validation (age 13–120, weight 20–500 kg, height 50–300 cm) with both UI-level gating via `_canProceed()` and a server-save safety net via `.clamp()`.

The midnight timer in HealthProvider fires at 00:00:00 the next day and re-subscribes all streams with a fresh date, chaining recursively. Edge case: DST fall-back or manual clock adjustment can delay the refresh by up to an hour, which is acceptable for a health tracker.

Scheduled notifications use `zonedSchedule` with `matchDateTimeComponents: DateTimeComponents.time` for daily repeats. `tz.local` is never set to the device's actual timezone — `flutter_timezone` is declared but never called — so all notifications fire at UTC offsets on devices outside UTC.

The reminder settings screen stores toggle state in-memory with no persistence. Revisiting the screen resets all toggles to off while scheduled notifications remain active in the OS, causing UI/state desync.

The premium screen is a UI shell with purchase flow entirely stubbed. The dashboard upsell card creates an expectation that something will happen on tap, but the user hits a dead-end SnackBar.

## Timezone initialization gap

The `notification_service.dart` `initialize()` method calls `tz_data.initializeTimeZones()` which loads the timezone database, but never calls `tz.setLocalLocation()` with the device's actual timezone. The `flutter_timezone` package is added to pubspec.yaml specifically for this purpose — its `FlutterTimezone.getLocalTimezone()` returns a string like `'America/New_York'` which should be passed to `tz.setLocalLocation(tz.getLocation(timezoneName))`.

Without this, `tz.local` defaults to UTC. Every `tz.TZDateTime.now(tz.local)` and every `tz.TZDateTime(tz.local, ...)` constructs UTC-relative times. A user in IST (+5:30) scheduling a 7 AM push-up reminder will get it at 12:30 PM local time.

```dart
// What's missing in initialize():
final timezoneName = await FlutterTimezone.getLocalTimezone();
tz.setLocalLocation(tz.getLocation(timezoneName));
```

Confirmed by searching the entire codebase — neither `setLocalLocation` nor `getLocalTimezone` appears anywhere.

## Reminder toggle cancel-and-reschedule pattern

Each toggle method (`_togglePushup`, `_toggleFoodLog`, `_toggleWater`) follows the same pattern when disabling: call `cancelAllReminders()` then re-schedule the reminders that are still enabled.

A crash or background kill between the cancel and the re-schedule loses all active notifications. The fix is straightforward: cancel only the specific notification IDs being disabled. The ID constants are already defined (`_pushupReminderId`, `_foodBreakfastId`, etc.) and could be cancelled individually.

The ephemeral UI state compounds this: if the user enables push-up reminders, leaves the screen, and returns, `_pushupEnabled` is `false`. Tapping the toggle "enables" it and calls `scheduleDailyPushupReminder` — the `cancel` before `schedule` inside that method prevents a true duplicate for that ID, but the UX of toggles not reflecting actual notification state will generate confusion and support tickets.

## Username validation inconsistency

`_validateUsername` at line 189 still throws a raw String:

```dart
throw 'Username must be 3–32 characters using letters, numbers, or _.';
```

This is called from `registerWithUsername` and `signInWithUsername` (via `_usernameAlias`). The call to `_usernameAlias` happens *before* the try/catch that wraps `_handleAuthException`, so this raw String throw propagates directly to the UI without being wrapped in `AppAuthException`. Callers using `catch (e)` + `e.toString()` still work, but it defeats the purpose of the typed exception class introduced in this PR.

## Delete account dead code path

The `deleteAccount()` method invokes a Supabase Edge Function and throws `Exception('Could not delete the account.')` on HTTP ≥ 400:

```dart
} catch (e) {
  final message = e.toString();
  if (message.contains('requires-recent-login')) { ... }
}
```

The string `'requires-recent-login'` is a Firebase Auth error code that cannot appear in the Supabase Edge Function response. The re-login prompt path is dead code. If session-expiry detection is needed, the Edge Function should return a structured JSON body with an error code, and the client should parse that instead of string-matching exception messages.

## Premium upsell with no backend

The `_PremiumUpsell` widget on the dashboard and the `PremiumScreen` itself create a purchase expectation with no fulfillment path. The `_handleSubscribe` method shows a SnackBar saying "coming soon." For users who see the upsell and tap through, this is a broken experience. Adding a visible "Coming Soon" badge on the dashboard card, or gating the upsell behind a remote config flag, would prevent negative first impressions until the purchase flow is wired.
