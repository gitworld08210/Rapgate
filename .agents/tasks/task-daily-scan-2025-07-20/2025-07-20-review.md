# Firebase remnant removal, onboarding validation, and withOpacity migration

This change eliminates compile-breaking Firebase references left over from a Supabase migration, adds input bounds-checking to the onboarding flow, and batch-migrates deprecated `.withOpacity()` calls to `.withValues(alpha:)` across three widget files. The Firebase cleanup is the highest-value fix: a stale `firebase_auth` import made `settings_screen.dart` un-compilable against the current pubspec. The onboarding validation prevents absurd values (age 0, weight 999) from flowing into calorie/protein target calculations. The `withOpacity` migration addresses Flutter 3.32 deprecation warnings in the files with the densest usage.

Watch for: The onboarding screen still has one un-migrated `.withOpacity()` call in `_genderOption` (confirmed). The delete-account error handler loses structured error information by string-coercing the exception (likely — depends on what `AuthService.deleteAccount` throws).

**Verdict**: APPROVED

## High-level view

The Firebase removal fixes a hard build failure: `firebase_auth` is absent from `pubspec.yaml`, so the import in `settings_screen.dart` broke compilation. The 18 deleted Firestore constants had zero remaining references. The only behavioral change is the delete-account catch clause, which now uses a generic `catch` and strips an "Exception: " prefix before displaying — but may expose raw internal formatting from Supabase's `AuthException`.

Onboarding validation is implemented as a dual gate: `_canProceed()` disables the "Next" button when body-stat values are out of range, and `_saveProfile()` re-validates with explicit error messages before writing to the backend. Both methods hardcode the same magic numbers (10/120, 20/300, 80/250), creating a maintenance coupling that could drift.

One `withOpacity` call in `onboarding_screen.dart` at line 298 (`AppTheme.primaryColor.withOpacity(0.05)`) was not migrated, leaving a deprecation warning in the same file that received all other changes.

## Missed withOpacity migration in onboarding_screen.dart

The diff migrates `withOpacity` in three files, but `onboarding_screen.dart` — which received the most substantive logic changes in this PR — still contains `AppTheme.primaryColor.withOpacity(0.05)` in the `_genderOption` widget (line 298). This is a confirmed omission: the file was clearly in scope for the migration, and the call sits in the same build method tree that was otherwise untouched.

## Delete-account error presentation

The old code handled `FirebaseAuthException` with structured fields (`e.code`, `e.message`) and surfaced a user-friendly message for `requires-recent-login`. The replacement:

```dart
catch (e) {
  ScaffoldMessenger.of(context).showSnackBar(
    SnackBar(
      content: Text(e.toString().replaceFirst(
          RegExp(r'^Exception:\s*'), '')),
    ),
  );
}
```

`e.toString()` on a Supabase `AuthException` yields something like `AuthException(message: ..., statusCode: ...)` depending on the supabase_flutter version. The regex only strips a leading `Exception: ` prefix, not the class wrapper. The user may see raw internal formatting. Low-severity UX concern, not a crash risk.

## Onboarding validation: duplicated range constants

The validation lives in two places: `_canProceed()` governs the button state (immediate feedback as the user types), and `_saveProfile()` acts as a safety net before the write. Both hardcode the same numeric ranges. If one is edited without the other, the button can enable while `_saveProfile()` rejects — or `_canProceed()` blocks while `_saveProfile()` would accept.

A single `_validateBodyStats()` helper returning a list of error strings (empty = valid) would let `_canProceed()` check `errors.isEmpty` and `_saveProfile()` display the errors, with no duplication.
