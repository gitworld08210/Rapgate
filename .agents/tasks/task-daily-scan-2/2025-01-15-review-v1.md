# Share Progress, onboarding validation, and scheduled reminders

Two commits that remove a stale Firebase reference, add input validation to onboarding, introduce a Share Progress screen with clipboard export, and wire up recurring hydration/food-log notifications via `flutter_local_notifications`. The feature commit ships two user-facing additions without adding new dependencies. Watch for: duplicate daily food reminders collapsing to the same delivery time (confirmed), notifications re-scheduled on every cold start without idempotency guard (confirmed), and no `POST_NOTIFICATIONS` permission request on Android 13+ (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The notification scheduling uses `periodicallyShow` with `RepeatInterval.daily` for both lunch and dinner reminders. Because `periodicallyShow` does not accept a time-of-day parameter, both will fire once a day at the same OS-determined offset from when they were first registered. The user gets two food prompts in quick succession rather than one at lunch and one at dinner. Hourly hydration is reasonable if the user can opt out, but the opt-out toggle doesn't exist in the UI yet.

The share feature imports `computeHealthScore` from `dashboard_tab.dart` via a `show` clause. This creates a cross-screen coupling — any refactor of the dashboard that moves or renames the function silently breaks the share screen.

Onboarding validation adds `autovalidateMode` and `validator` callbacks, but the "Next" button uses a separate `_isCurrentStepValid()` method with its own bounds checks. The two paths agree on ranges today but have no shared source of truth, so they can silently diverge.

The delete-account catch block uses string-matching on `e.toString()` to detect re-authentication requirements. This is brittle against SDK message changes but is the only option without typed exceptions from the Supabase auth layer.

## Notification scheduling: duplicate food reminders and timer reset

The `scheduleFoodLogReminder()` method creates two `periodicallyShow` calls both using `RepeatInterval.daily`:

```dart
await _localNotifications.periodicallyShow(
  _foodLunchNotificationId,
  'Log your meal 🍽️', ...
  RepeatInterval.daily, ...
);
await _localNotifications.periodicallyShow(
  _foodDinnerNotificationId,
  'Evening check-in 🌙', ...
  RepeatInterval.daily, ...
);
```

`periodicallyShow` fires at inexact intervals anchored to the registration time. Both registrations happen within milliseconds of each other inside `initialize()`, so both fire at roughly the same moment each day. The user receives two food notifications in a burst, not one at lunch and one at dinner. The only fix within the current dependency set is to drop one of them and accept a single daily food reminder, or add the `timezone` package and switch to `zonedSchedule`.

`initialize()` unconditionally calls `cancel` then `periodicallyShow` on every cold start. On Android, `periodicallyShow` schedules via `AlarmManager` with the *current time* as the anchor. Every app relaunch resets when the first reminder fires. A user who opens the app at 11pm will get their first hydration reminder at midnight, then hourly from there — including overnight. Guarding with a persisted flag (set once, cleared only on explicit opt-out) would stabilize the schedule.

## Android 13 notification permission gap

On Android 13 (API 33) and above, apps must request `android.permission.POST_NOTIFICATIONS` at runtime before notifications appear. The `initialize()` method goes straight to scheduling without any permission request. On these devices, all scheduled reminders will be silently dropped until the user grants permission through some other code path. The `flutter_local_notifications` package provides `resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()?.requestNotificationsPermission()` for this purpose.

## `computeHealthScore` coupling

The share progress screen imports the health score function via:

```dart
import 'dashboard_tab.dart' show computeHealthScore;
```

`computeHealthScore` is a pure function with no dependency on widget state. Extracting it to `lib/utils/health_score.dart` would let both screens import it without creating a cross-screen dependency, and would make the function discoverable for future callers and testable in isolation.

## Delete-account string matching

```dart
} catch (e) {
  final errorMsg = e.toString().toLowerCase();
  if (errorMsg.contains('requires-recent-login') ||
      errorMsg.contains('recent login') ||
      errorMsg.contains('reauthenticate')) { ... }
}
```

Any change in exception message wording from the Supabase SDK will bypass the re-auth branch and show the generic "Failed to delete account" error. The "re-auth required" scenario would silently degrade to a confusing generic message. Since Supabase's GoTrueException doesn't expose a stable error code in the Dart client, this is the best available option — but worth noting as a maintenance risk.

## Onboarding dual-validation design

The validators and `_isCurrentStepValid()` perform the same bounds checks independently. The validators fire on user interaction (red text beneath the field), while `_isCurrentStepValid()` gates the "Next" button. The two validation paths should share a single validation function to prevent future divergence (e.g., someone changes the weight upper bound in one place but not the other).
