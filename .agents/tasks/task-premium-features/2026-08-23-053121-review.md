# Premium features: tiered unlock, rest days, AI summaries, badges, leaderboard, height measurement, and dark mode audit

This change adds the full premium feature suite to RepGate: tiered push-up unlock durations (4h/12h/24h based on reps), fine escalation on consecutive misses, rest day passes as streak shields, emergency unlock with penalty fine, customizable water goals, a midnight stream refresh, weekly AI health summaries via Gemini, seven achievement badges with push notifications, quick-log meal favorites, a social leaderboard over accountability links, comprehensive dark mode fixes across all screens, premium animation widgets (wave, shimmer, glass, haptic), and camera-based height measurement using ML Kit pose detection. The service rename from `FirestoreService` to `DatabaseService` cleans up legacy naming. Four SQL migrations add the required schema.

**Watch for:** The height measurement tool uses a hardcoded 300 cm distance and a fixed vertical FOV calculation that assumes 16:9 portrait — real-world accuracy depends heavily on these constants matching the device (confirmed). The `get-leaderboard` edge function exists but the client calls the Postgres RPC directly, creating a redundant and potentially confusing code path (confirmed). The `check-achievements` cron function makes up to 14 individual DB queries per user per badge, which scales poorly once the user base grows (confirmed). Emergency unlock creates a fine row with column names that may not match the `fines` table schema (`amount` vs the schema's `amount_paise`) (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The tiered unlock system replaces the flat 24-hour reward with a graduated incentive: 5 reps earns 4 hours, 10 earns 12 hours, 15+ earns the full 24. The implementation spans both the Edge Function (`computeUnlockHours`) and a client-side constant table in `AppConstants.unlockDurationTiers`. Keeping both in sync is a manual discipline — if the server tiers change, the client label breaks silently.

Fine escalation uses a `consecutive_misses` counter on the `streaks` table, reset when push-ups are completed via `bump_pushup_streak`. The daily check function reads the counter, increments it, then calls `compute_escalated_fine`. The race window between reading and updating `consecutive_misses` in the Edge Function is narrow but exists: two concurrent cron invocations could produce incorrect escalation.

Rest day passes are earned every 7 days of streak (capped at 3) and consumed through an edge function that delegates to a `SECURITY DEFINER` Postgres function. The pass usage inserts a dummy verified session with `rep_count: 0` — downstream consumers of `pushup_sessions` that filter by `status = 'verified'` will accidentally count these phantom rows in the leaderboard and badge checks.

The camera-based height measurement uses ML Kit pose detection to find head-to-feet pixel distance, then applies a pinhole camera model with a hardcoded 300 cm subject distance and a derived vertical FOV. The math inverts the aspect ratio assumption (uses 16/9 to compute vertical FOV from horizontal), meaning landscape launches or non-standard sensors will produce wrong heights. The 5-reading consistency check rejects noisy frames, but absolute accuracy depends entirely on the assumed distance being correct.

The weekly AI summary calls Gemini Pro with a structured prompt per user, rate-limited to 200ms between calls. Malformed Gemini responses fall back to raw text with empty insights, which is safe but produces a degraded user experience without surfacing why.

The social leaderboard's `get_leaderboard` Postgres function is called directly from the client via RPC. The `get-leaderboard` edge function is dead code — it wraps the same RPC but nothing invokes it.

<summary>Issues (8)</summary>

1. **Emergency unlock fine column mismatch** — The `emergency-unlock` edge function inserts into `fines` with `{ amount: ... }` but the existing schema likely uses `amount_paise`. Verify the column name or the insert will silently fail. The insert result is also not checked for errors.
2. **Dead `get-leaderboard` edge function** — The client calls the `get_leaderboard` RPC directly via Supabase client. Remove the edge function or route the client through it to avoid confusion about which path is authoritative.
3. **Height measurement distance assumption** — `defaultDistanceCm = 300.0` and the vertical FOV inversion (16:9 aspect ratio) are hardcoded. On devices with different FOVs or when the user is not at 3m, the measurement is unreliable. Consider surfacing a calibration step or at minimum documenting the accuracy bounds in the UI.
4. **Achievements cron N+1 query pattern** — `checkWaterChampion` and `checkCleanEater` execute up to 14 sequential single-day queries per user. At 1000 users this is 28,000 queries per cron run. Batch into a single aggregation query per user.
5. **Rest day pass phantom sessions** — Inserting `status: 'verified', rep_count: 0` makes these visible to any query that counts verified sessions (weekly pushups in leaderboard, century club badge, first pushup badge). Filter by `rep_count > 0` or use a separate status like `exempt`.
6. **Tiered unlock client-server sync** — `AppConstants.unlockDurationTiers` in Dart must mirror `UNLOCK_TIERS` in `pushup.ts`. A mismatch causes the pushup screen to display wrong reward text. Extract to a shared source or have the server response include the granted duration.
7. **`consecutive_misses` read-then-update race** — The daily check reads `consecutive_misses`, adds 1 in TypeScript, then writes it back. If the cron function runs concurrently (e.g., retry), the counter could skip or duplicate. Use a single `UPDATE ... SET consecutive_misses = consecutive_misses + 1 RETURNING consecutive_misses` instead.
8. **`earn_rest_day_pass` never called** — The SQL function exists but no Edge Function or trigger invokes it. Users cannot currently earn rest day passes. Wire this into `bump_pushup_streak` or the daily check.

## Emergency unlock fine schema mismatch

The `emergency-unlock` edge function (line 76-82) inserts a fine record:

```ts
await adminClient.from("fines").insert({
  user_id: user.id,
  amount: fineAmount,
  reason: "emergency_unlock",
  status: "pending",
});
```

The fine escalation migration (`004_fine_escalation.sql`) uses `create_fine_if_missing` with parameter `p_amount_paise`, and the existing `FineModel` in Dart maps `amount` from the row. If the actual Postgres column is `amount_paise` (matching the RPC parameter naming), this insert silently drops the amount or errors. The error isn't caught — the Edge Function proceeds to return success to the client even if the fine insert fails.

## Height measurement: fixed-distance pinhole model

The `HeightCalculator.estimateHeightProportional` method computes:

```dart
final aspectRatio = 16.0 / 9.0;
final verticalFovRadians = 2.0 * atan(aspectRatio * tan(fovRadians / 2.0));
```

This converts a horizontal FOV to vertical FOV assuming 16:9 portrait. Several issues compound:

1. Phone cameras report FOV differently — some sensors have wider vertical than horizontal in portrait mode depending on the sensor orientation relative to the device.
2. The `defaultDistanceCm = 300.0` is never validated. The UI instructions step says "stand 3 meters away" but there's no distance measurement or verification.
3. The `applyCameraHeightCorrection` assumes a known `cameraHeightCm` which is never measured or input by the user.

The `requiredConsistentReadings = 5` with `maxVarianceCm = 3.0` ensures internal consistency but not absolute accuracy. A person at 2m distance would be consistently overestimated. The UI should communicate this is an estimate, not a clinical measurement. A calibration step (known reference object, or letting the user confirm/adjust distance) would significantly improve reliability.

## Achievements cron: O(N×14) query pattern

`checkWaterChampion` and `checkCleanEater` both execute a loop:

```ts
for (let i = 0; i < 14; i++) {
  const { data: logs } = await adminClient
    .from("water_logs")
    .select("amount_ml")
    .eq("user_id", uid)
    .gte("logged_at", dayStart.toISOString())
    .lt("logged_at", dayEnd.toISOString());
  // ...
}
```

That's 14 round-trips per user per badge. With 7 badges total and serial processing per user, at 500 users this becomes ~14,000 queries in a single cron invocation. A single aggregation query per badge per user (group by date, sum amounts, then check consecutiveness in application code) would reduce this to 2 queries per user.

## Rest day phantom sessions in downstream queries

The `use_rest_day_pass` SQL function inserts:

```sql
INSERT INTO pushup_sessions (
  user_id, status, rep_count, reason,
  started_at, completed_at
) VALUES (
  p_user_id, 'verified', 0, 'rest_day_pass',
  now(), now()
);
```

The leaderboard function counts weekly verified sessions:

```sql
SELECT COUNT(*)::bigint AS weekly_count
FROM public.pushup_sessions ps
WHERE ps.user_id = lu.uid
  AND ps.status = 'verified'
  AND ps.started_at >= week_start
```

This counts rest-day-pass sessions toward weekly pushups. `checkCenturyClub` counts all sessions with `status = 'verified'` — rest days inflate that count. `checkFirstPushup` would fire if the user's only interaction was a rest day pass, contradicting the badge's meaning. Add `AND rep_count > 0` or `AND reason IS NULL` to these queries.

## `earn_rest_day_pass` is orphaned

The SQL function `earn_rest_day_pass(p_user_id)` awards a pass when `current_pushup_streak % 7 = 0`, but nothing calls it. The `daily-pushup-check` Edge Function doesn't invoke it. The `bump_pushup_streak` SQL function doesn't call it either. Users accumulate passes at a rate of zero. Either wire `earn_rest_day_pass` into `bump_pushup_streak` (called on successful session completion) or invoke it from the daily check for users who just crossed a 7-day boundary.

## `consecutive_misses` race condition

The `daily-pushup-check` function reads the current value, adds 1 in TypeScript, and writes it back:

```ts
const { data: streakRow } = await adminClient.from("streaks").select("consecutive_misses").eq("user_id", uid).maybeSingle();
const currentMisses = (streakRow?.consecutive_misses ?? 0) + 1;
await adminClient.from("streaks").update({ consecutive_misses: currentMisses }).eq("user_id", uid);
```

If the cron retries or runs concurrently, this read-modify-write sequence can produce a stale increment. Replace with an atomic update: `UPDATE streaks SET consecutive_misses = consecutive_misses + 1 WHERE user_id = $1 RETURNING consecutive_misses` — or create a small RPC that does both the increment and the fine computation in a single transaction.
